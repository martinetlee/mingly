1 · Big picture

Mingly is a single desktop app with two halves that run together on your Mac. The frontend (React) draws the screens. The backend (Python, FastAPI) does everything else: it talks to Telegram, Signal, SMS and Gmail, stores the data in SQLite, and calls the LLMs.

The folders around it (mingly-all/)

mingly/the app

Everything on this page. backend/, frontend/, tests/, build_app.sh + mingly.spec (PyInstaller packaging).

ScamDetectionPoC/research

Trains the LightGBM scam models. Mingly doesn't import it: it ships the trained files in backend/scam/ml_models/ and repeats the feature extraction in scam/tools/ml_prefilter.py.

mingly-cloud/empty

Git repo with a single "Initial commit" and no code yet. The *_SPEC.md files in mingly-all/ are the design docs for it and for Shield.

4 · Where frontend and backend meet

The two halves share no code. They connect through four contracts. Changing one side of a contract means changing the other.

Requests (REST)

api/client.ts, email.ts, calendar.ts…
→
backend/api/*.py routers, wired in router.py

Every call carries the X-Session-Token header. It's checked in api/dependencies.py.

Data shapes

backend/serializers.py
=
frontend/src/api/types/

The JSON shape of Conversation, Message, Person and Identity. The two files must agree.

Live updates (WebSocket)

backend/ws/manager.py broadcast
→
lib/ws.ts → context/WebSocketContext → hooks

Events such as new_message, person_changed and connector_status arrive on /api/ws.

Streams (SSE) & packaging

briefing/events.py
→
pages/intelligence/useBriefingJob.ts

For the release build, vite build outputs frontend/dist, which api/router.py serves. In dev, Vite on :5173 proxies /api to :8765.

5 · How it stays layered

Every arrow above points down a layer or sideways within one, with no cycles. That's checked by tests, so it can't drift back.

tests/test_architecture.py (backend)

Every backend.* import, including ones inside functions, must point to the same or a lower layer. The module graph must be acyclic. fastapi/starlette may appear only in api/, ws/ and main.py. Telethon and the Telegram client/runtime may appear only in backend/telegram/.

frontend/src/__tests__/architecture.test.ts

api/ and lib/ never import UI. hooks/ never imports components or pages. Nothing outside pages/ imports a page, and no screen folder imports another. Every relative import and vi.mock path must resolve.

Ports instead of upward imports

Ingest exposes a MessageInspector port and Shield plugs into it through backend/wiring.py. Sessions notify revocation listeners and the WebSocket manager subscribes. The connector manager tells a connector on_reauthorized.

Connector roles

Routes ask connector_with(conv, Role, …) and never branch on the channel. Telegram's code (send, albums, edit/delete/forward, pins, dialogs, members, topics, admin, history, search, address book, directory) lives in backend/telegram/. tests/test_telegram_routes.py pins every Telegram route's calls and responses; it passed unchanged before and after the move.

Domain errors

Lower layers raise backend.errors types (503, 401, 404, 400, 429), and one API handler maps them. No HTTP types appear below the API.

Deliberate exceptions

MCP tool handlers (api/mcp_tools/) keep their own paginated queries: they're the resolvers of an external read API. Telegram converts Telethon messages itself, then shares the same crud.save_messages, people.identities and ingest.fanout as every channel. 44 imports stay inside functions, all on purpose: late binding for patched singletons, optional dependencies, and Shield-only startup.
